# etdd-reference

A worked demonstration of **Extreme TDD** (ETDD) on a small, fully agent-built codebase: a Python 3.11+ CLI library-loan tracker. Three features under full ETDD treatment. The repo's center of gravity is `specs/outcomes/` and `tests/`; `src/` is regenerable.

ETDD is documented in the companion program at [`extreme-tdd-program`](https://github.com/larsappel/extreme-tdd-program) — see `docs/publish/manifesto.md` and `docs/publish/practitioner.md` for the Concept this repo demonstrates.

## Provenance

**Human co-specifier:** `lars-appel` (Lars Appel — [@larsappel](https://github.com/larsappel)).

Production code in this repo is generated by agents working under the **three-author rule**: for every ETDD-treated feature, three distinct agent identifiers play the roles of outcome-document-author (writes `specs/outcomes/<slug>.md`), test-author (writes `tests/test_<slug>.py`), and implementation-author (writes the code under `src/`). No agent occupies more than one of those roles for any feature.

Agent identities and the prompts they ran on are archived in [`PROMPTS.md`](./PROMPTS.md). Per-feature attributions also appear in commit-message trailers (`Agent: <role>-<id>`).

## What this demonstrates

Each test file traces to at least one of the manifesto's seven principles. Each of the seven principles is demonstrated by at least one test, outcome document, or repo-level structural decision. The mapping is tracked in `PROMPTS.md` and via per-test comments.

| Principle | Demonstrated by |
|-----------|-----------------|
| P1 — Tests are the prompt. | Every feature: the outcome is the brief; the test is its executable form. |
| P2 — Intent is human; execution is delegated. | Outcomes are human-authored / co-specified; tests + code are agent-built. |
| P3 — Red — Delegate — Verify. | Commit history per feature shows outcome → failing test → green implementation. |
| P4 — Coverage is constraint. | `free_dimensions:` in outcome frontmatter; unstated requirements are free. |
| P5 — Specify behavior, not implementation. | Outcomes name edge cases; not call shapes. |
| P6 — No agent writes both the spec and the code. | Three-author rule per feature; agent identifiers in `PROMPTS.md`. |
| P7 — The suite is the source of truth. | `src/` is regenerable. The suite is what we version. |

## How to read this repo

1. Start in `specs/outcomes/` — the human-authored declarations of behavior.
2. Read the matching file in `tests/` — the executable form of the outcome.
3. Glance at `src/library_loan/` for plausibility.

This reading order is the practitioner-guide order applied to the repo.

## How to run it

```bash
python -m pip install -e ".[dev]"
pytest
python scripts/check_pairing.py
```

CLI entry point is wired per feature as outcomes land; see `pyproject.toml` `[project.scripts]`.

## Adversarial pass

At least one feature receives an adversarial (breaker) pass per Pattern 5 of `01-implementation-patterns.md`. The result is recorded at `docs/process/breaker-<feature>.md` regardless of whether a break was found. The feature chosen and the result are named here once the breaker has run (G5b).
